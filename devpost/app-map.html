Skill Pack — How To Use

A one-page, bilingual (English / Vietnamese) guide to the Devpost Learn Build With AI: Basics skill pack. Visitors click through a simulated version of the 7 real steps (install, then /1-start … /6-ship), learn why the method works, and pick up tips. Everything runs in the browser: no server, no account, no API key.

The main pieces

Content (data)

content/en.ts and content/vi.ts hold every visible word. content/stages.ts describes the 7 stages as scripts.

Simulator

components/simulator/ “plays” a stage script: terminal lines, agent chat, files appearing, and the generated document.

Memory

lib/providers.tsx and lib/storage.ts keep language, theme, sound, mode and progress in the browser’s localStorage.

Other sections

components/why/ (drag-and-drop game), components/TipsSection.tsx, components/SiteFooter.tsx.

One action, end to end

The action: on an interview stage (e.g. /1-start), the visitor clicks Run, picks a preset answer, and the answer appears inside learner-profile.md in the devpost/ tab.

Reference route (3 stops)

A reference route, not a completed tour. Open the project in your editor and search for the anchors below.

1

components/simulator/StageControls.tsx · StageControls

Decides the one button the stage needs right now: Run, the preset answers (or Approve / Fix), or Next stage. Clicking calls onRun / onAnswer.

2

components/simulator/JourneySimulator.tsx · function run, function answer, function complete

run() starts playback, and a useEffect reveals one line every 380 ms (STEP_MS). answer() saves the choice with updateProgress. complete() marks the stage done, plays a sound, and switches to the devpost/ tab. Progress is stored as JSON under skillguide:progress (lib/storage.ts · writeRaw, parseProgress).

3

components/simulator/DocPreview.tsx · DocPreview (+ buildDocs in JourneySimulator)

buildDocs takes each stage’s doc lines from the dictionary. DocPreview replaces {answer} with the chosen answer’s text and highlights it in pink.

A practice to reuse

Write acceptance criteria as something you can observe, then check exactly that. The PRD said: “Switching language changes every visible text on the page with no leftover strings in the other language” (prd.md › Language, Theme, and Sound Toggles). Because it was observable, it became a mechanical check: load the page in each language, then search the visible text for every sentence from the other dictionary. It passed in both directions. When the default language was changed to English at the final review, the same check was re-run and passed again in both languages.

Some criteria can only be judged by looking. A screenshot taken during slice 4 showed that the Georgia font broke Vietnamese diacritics in the decision-game preview, which no text check would have caught. Switching to Lora fixed it.

On your next project: for each feature, ask “what would I see if this works?”, write that down in the PRD, and have the agent turn it into a check it runs after every step.
